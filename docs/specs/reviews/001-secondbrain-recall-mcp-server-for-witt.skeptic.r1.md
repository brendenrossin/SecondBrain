## Skeptic review — 001 SecondBrain recall MCP server for Witt
Verdict: approve with changes

Unstated assumptions:
1. The API process reindexes through `check_and_reindex`. Not true: the live path is `POST /api/v1/index` → `_run_indexing` in `src/secondbrain/api/index.py`. `check_and_reindex` (`api/dependencies.py:277`) is only called from the deprecated Gradio `ui.py:438,636`. Not written down, and the spec states the opposite in three places.
2. With tracing on, the recall path emits no spans. Not true by default: `Traceloop.init` (`tracing.py:95`) auto-loads the installed instrumentors, and `opentelemetry-instrumentation-chromadb` is in `uv.lock` as a traceloop-sdk dependency. Not written down.
3. Embeddings are local, so recall "costs nothing". It only holds while `SECONDBRAIN_EMBEDDING_PROVIDER=local`; with `openai`, every recall is a paid API call. Implied by PROJECT.md, not stated in the spec.
4. `retrieve()` returns enough candidates for dedupe and post-filters to still fill `limit` notes. Not written down: the spec never says what `top_k` the endpoint passes.
5. The vault root is `main-vault`, so every Witt path starts with `Witt/`. PROJECT.md says so and `extract_note_metadata` takes the first path segment, so this is safe, but the spec should say it.
6. Learnings exist. There are none today. The vault has 7 Witt files: 2 hubs, 2 ADRs, 2 spec mirrors and 1 log, with no `Learnings/` folder. The "plus all Learnings" behaviour and the `learning` kind have no live data. Not written down. The spec also says "5 Witt .md files", which is stale.
7. The API's reindex runs under `.reindex_lock`. Only the dead `check_and_reindex` takes that lock; `_run_indexing` doesn't. PROJECT.md repeats the same error, and Decision 1 relies on it.

- [x] **BLOCKER** Acceptance criteria and Design target the wrong reindex code path. The diagram node `I[check_and_reindex]`, Decision 3 ("Step 3 of `check_and_reindex`"), Decision 4 (malformed YAML) and the scenarios "previously indexed logs are removed…" and "malformed frontmatter skips the note…" all exercise `check_and_reindex`. Production reindexing (`make index`, daily_sync's POST, Rollout step 3) goes through `_run_indexing`. The two behave the same today, but the new tests would pin dead Gradio code and leave the live path unguarded, and the two have already drifted (lock, epoch file, embedding cache). Fix: point the diagram, decisions and scenarios at `api/index.py::_run_indexing` / `POST /api/v1/index`, either instead of or as well as `check_and_reindex`. Also correct Decision 1's `.reindex_lock` argument. — resolved: all reindex references now target POST /api/v1/index → _run_indexing; Decision 1 lock claim corrected; PROJECT.md fix in Rollout step 8.
- [x] **BLOCKER** Goal 5 ("Recall adds no spans") and Decision 6 are false as designed. `api/recall.py` not importing tracing changes nothing: once the lifespan runs `init_tracing`, Traceloop's chromadb instrumentor wraps `collection.query` process-wide, so every recall writes chroma spans to `data/traces/*.jsonl`. They probably have the same shape as `/ask`'s retrieval spans, so the format contract likely holds. The volume doesn't: agents calling recall from every session will flood the JSONL with retrieval-only spans. That can skew trace-eval's sampling tests (`test_sample_has_llm_traces`, `test_sample_includes_multiple_types`), and Goal 6's "0 skipped, 9 passed" can't establish anything about it. Fix: pick one. — resolved: option (b) chosen by Brent, suppress_instrumentation around retrieval; zero-spans scenario with an instrumentation-is-live control; trace-eval run after real recall traffic.
  - (a) Reword Goal 5 and Decision 6 to "no new span *shapes*; recall emits the same chroma spans as `/ask`", and add a Risk on volume.
  - (b) Suppress instrumentation around the recall call, using OTel's suppress-instrumentation context key, and add a scenario: tracing on, POST recall, 0 new lines in today's JSONL.
- [x] **SHOULD** Candidate pool size is unspecified. Dedupe-per-note plus the `project`/`kinds` post-filters run after `retrieve(query, top_k=?)`. If the endpoint passes `top_k=limit`, it routinely returns fewer than `limit` notes; if it passes all candidates, latency and the semantics change. Two engineers will build this differently. Fix: state it, e.g. "retrieve with `top_k = k_vec + k_lex` (the whole fused set), then filter, dedupe and slice to `limit`". — resolved: Decision 6 states top_k = k_vec + k_lex then floor → filters → dedupe → slice.
- [x] **SHOULD** `project` combined with `scope="vault"` is undefined. Does it return only that project's Witt notes plus Learnings, or do all non-Witt notes pass through? Same question for `kinds=["note"]` with `scope="witt"`. Fix: specify the semantics, or reject the combination with a 422. — resolved: Decision 6 semantics: project applies in both scopes (that project + Learnings); kinds=['note'] with scope=witt → 422.
- [x] **SHOULD** Contradiction on `kind="note"`. `RecallHit.kind` says "note" only appears with `scope="vault"`, but `classify_witt_path` maps any unrecognized Witt path to "note". Examples are `Witt/README.md`, `Witt/Projects/witt/scratch.md`, and anything Witt adds before its Data contract freezes. Those show up under `scope="witt"`. Fix: drop the "only with vault" claim, or add a kind such as `other`, and add one unrecognized-Witt-path row to the classification table. — resolved: new kind 'other' for unrecognised Witt paths; table rows added.
- [x] **SHOULD** The eval is contaminated by the spec mirrors. `Witt/Projects/second-brain/specs/001-secondbrain-recall-mcp-server-for-witt.md` is a Witt spec, so it is in scope. It contains the ADR-001 example query ("can an override let a full spec skip review?") and the ADR's filename verbatim. The live eval, and anyone checking the ADR-001 scenario against the real index, can find this spec ranking first. Fix: build eval queries that aren't quoted in any indexed spec mirror, or exclude the spec under test from labels. Note the leak in Evals. — resolved: Evals require fresh queries not verbatim in any indexed note; this spec quotes no eval queries.
- [x] **SHOULD** The eval thresholds can't fail meaningfully. There are 6 eligible notes, `limit=5` and dedupe per note, so almost any query returns 5 of the 6 notes and recall@5 ≥ 0.9 is nearly guaranteed. The `kinds=["learning"]` queries and "plus Learnings" have no data at all. The spec admits this but still calls the threshold a gate ("Run manually before Implemented"). Fix: make recall@5/MRR report-only until the corpus passes about 30 notes, keep scope isolation as the only hard gate, and seed one Learning fixture for the unit scenarios. — resolved: hard gates are scope isolation, null false positives, latency and stale labels; ranking report-only until 30 notes; unit fixtures include a Learning.
- [x] **SHOULD** The open question on logs vs `/ask` should be settled before Approved, not after. It changes Decision 3, Goal 4, the Data section and two scenarios. The alternative (keep logs indexed and post-filter them out of recall) is a materially different design. Also note the side effect the spec omits: `api/metadata.py` and `daily_sync.extract_metadata` use the same `VaultConnector`, so metadata extraction stops seeing logs too. That is probably good, but it should be stated. — resolved: Brent approved excluding logs before review; metadata-extraction side effect stated in Decision 3.
- [x] **NIT** "Never raises" in the MCP tool isn't fully in the handler's control. With `filters: RecallFilters | None` (`extra="forbid"`), the MCP SDK validates arguments before calling the function, so a bad filter key becomes an SDK tool error, not `{"ok": false}`. Either type `filters` as `dict | None` and validate inside, or scope the claim to transport and HTTP errors. — resolved: MCP tool takes filters: dict | None and validates inside; scenario 'invalid filters return ok false'.
- [x] **NIT** "Costs nothing / no LLM calls" should say "with local embeddings". With the OpenAI provider, each recall is an embeddings API call and sends the query off-machine. That matters given the local-first rule. — resolved: Decision 10 and Intent qualify 'no network calls' to the local embedder.

Cheaper alternative considered: There are 6 Witt notes and no Learnings, so the skills could get most of today's value by running Grep over `~/Obsidian-Vault/main-vault/Witt/` with no new code. When semantic recall does earn its keep (past about 30 notes), the thin HTTP client could live as a `recall` tool in Witt's existing MCP server, which is the consumer and already depends on `mcp`. That avoids a second MCP server, a second user-scope registration and a new dependency in SecondBrain. The `/api/v1/recall` endpoint and the store pre-filter are the right, cheap core either way.
