- [x] **BLOCKER** The `latency` hard gate reads a field the response doesn't have. Evals says p95 is "measured from each response's server-side `latency_ms`", and the gate row says "responses with latency_ms 1200 at p95". But `RecallResponse` (Interfaces) has no `latency_ms`; it exists only in `data/recall_log.jsonl`. `response_model=RecallResponse` would also strip any extra key. The same gap hits the report pins "Witt chunk count" and "empty-blurb count": the eval "never opens the stores" and talks only HTTP, and no response field or endpoint returns either value. — Broken implementation that passes: the stubbed-transport test fakes `latency_ms` in the JSON, so the gate passes in unit tests and either crashes (`KeyError`) or reads nothing against the real API. Or the eval quietly falls back to client wall-clock, which is the source r3 ruled out. — Pick one source and pin it. Either add `latency_ms` (and, if wanted, `witt_chunk_count`) to `RecallResponse`, or have the eval join `recall_log.jsonl` by `request_id`. Then rewrite the gate row against that source, e.g. `test_latency_gate_reads_<source>`. For empty-blurb count, name where it comes from or drop it from the report. — resolved: v0.5.0: RecallResponse gains latency_ms and witt_chunk_count; latency gate reads the response field; empty-blurb count dropped from the report (floor_margin replaces it).

- [x] **SHOULD** The floor is only tested at its default, so a hardcoded floor passes. Every scenario uses `recall_min_similarity = 0.40`, the default. — Broken implementation that passes: `HybridRetriever(..., min_similarity=0.40)` hardcoded, or passing the floor nowhere and relying on a mocked vector store that already returns only values at or above 0.40. — `test_recall_uses_configured_floor`: with `recall_min_similarity=0.55`, the retriever is built with `min_similarity=0.55`. With a real `VectorStore` over the fixture, a chunk at 0.50 is absent, one at 0.55 is present, and the log line's `recall_min_similarity` is 0.55. — resolved: v0.5.0 AC 'the configured floor is used, not a constant' (0.55 on real stores, log value).

- [x] **SHOULD** No scenario has RRF order differ from similarity order, so "BM25 still shapes the ranking" (Decision 6) and "sort by RRF" (step 10) are unverified. With the stub embedder, similarity and RRF order can coincide. — Broken implementation that passes: sort hits by `similarity`, or ignore lexical results entirely. "Hits are sorted by score descending" still holds if `score` happens to follow the same order. — `test_bm25_reorders_vector_candidates`: note A has similarity 0.80 and no lexical match; note B has similarity 0.70 and is lexical rank 1. Assert B is first, `B.score > A.score` and `A.similarity > B.similarity`. Also add a row to the limit scenario where a note's highest-similarity chunk is not its highest-RRF chunk, and assert the snippet comes from the highest-RRF chunk. As written, a "keep max similarity" dedupe passes. — resolved: v0.5.0 AC 'BM25 reorders vector candidates', plus a highest-RRF-not-highest-similarity line in the limit scenario.

- [x] **SHOULD** Decision 6's premise ("vector search returns **every** Witt chunk at or above the floor") is never checked on real Chroma. Chroma's filtered HNSW query is approximate. The crowding scenario uses one Witt chunk and doesn't say whether the stores are real or mocked. — Broken implementation that passes: mocked stores that honour `include_folders` trivially, while real Chroma with `where` plus HNSW drops some Witt chunks. Keyword-only chunks then get dropped when they should have scored. — State that "the pre-filter survives crowding" runs on the real `LexicalStore`/`VectorStore` over the committed fixture (that also exercises the FTS JOIN; `chunk_id` is ambiguous once `chunks` is joined). Add `test_vector_window_returns_all_witt_chunks`: fixture with N Witt chunks among ≥10×N `10_Notes` chunks, floor 0.3 with every Witt chunk above it, and `search(k=N, include_folders=["Witt"])` returns exactly N ids, equal to `count_chunks(["Witt"])`. — resolved: v0.5.0: crowding scenario runs on real stores; new AC 'the vector window returns every Witt chunk (real Chroma)'; Decision 6 states the assumption.

- [x] **SHOULD** The MCP "never raises" claim covers only `httpx.HTTPError` and malformed `hits`. — Broken implementations that pass:
  - `data["warnings"]` on a 200 body `{"hits": []}` raises `KeyError`. The SDK turns that into `isError`, which the "never raises" contract forbids.
  - An injected client whose `post` raises a non-httpx exception (`ValueError`, `RuntimeError`) also escapes. — resolved: v0.5.0: catch-all except Exception in the handler; failure-table row for ValueError; sparse-200 scenario pinned ok true with defaults.

  Fix: add rows to the failure table:
  - `200 {"hits": []}` with no `warnings`/`notices`/`request_id`: pin either ok true with defaults or ok false "invalid response".
  - `client.post raises ValueError`: ok false, error contains `ValueError`, not isError.

  Implement this as a catch-all `except Exception` in the handler.

- [x] **SHOULD** The request-id correlation that Decision 9 promises isn't asserted on the failure path.
