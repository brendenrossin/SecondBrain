- [x] **BLOCKER** The floor is only tested with everything below it. "The similarity floor turns an unrelated query into an empty result" has every candidate below 0.5. — Broken implementation that passes: `if settings.recall_min_similarity > 0: return []`. It also can't tell `<` from `<=`, or "floor before dedupe" (Decision 6 step 3) from "floor after dedupe" (step 6). — Add `test_floor_keeps_above_drops_below`: floor 0.5, chunks at 0.62, 0.50 and 0.49, plus one BM25-only chunk. Assert exactly the notes for 0.62 and 0.50 come back. Assert `dropped_below_floor == 2` exactly, and state whether it counts chunks or notes. Add `test_floor_applies_before_note_dedupe`: a note whose top-RRF chunk is BM25-only (similarity 0) and whose second chunk has similarity 0.7 returns that note, with the 0.7 chunk's snippet, similarity and score. — resolved: boundary scenario (0.62/0.50/0.49 + rescored keyword-only 0.31) with exact hits and counts; floor-before-dedupe scenario.
- [x] **BLOCKER** The "fills the limit" scenario doesn't prove `top_k = k_vec + k_lex`. "Only decision notes rank below 6 higher-scoring … chunks" puts the decisions at fused ranks 7–8, still inside `retrieve`'s default `top_k=10`. — `retriever.retrieve(query)` with the default `top_k`, then filtering, passes. — Raise it to at least 12 higher-ranked non-decision chunks, or also assert `retrieve` was called with `top_k == retriever.k_vec + retriever.k_lex` and the scope's folder kwarg. — resolved: decisions now rank below 12 chunks, and the Witt-only scenario asserts top_k == k_vec + k_lex with include_folders.
- [x] **BLOCKER** The "existing callers are unaffected" golden is tautological if it is captured from the modified code ("golden output captured in the test"). It is the only proof of the "No refactor" claim. — Passing `where={}` or `where=None` to `collection.query`, or rewriting the FTS SQL with an always-true JOIN that changes tie order, passes a golden captured after the change. — Capture the golden on `main` before any change and commit it as a fixture. Also assert directly that with no folder kwargs `collection.query` gets no `where` key, and that the lexical SQL text and bound params equal today's `(escaped_query, top_k)`. — resolved: goldens captured on main and committed as fixtures (Rollout 1); asserts no 'where' key and unchanged SQL and params.
- [x] **BLOCKER** The eval's null-query hard gate is circular. Calibration puts the floor at the midpoint between the max null top-hit and the min labelled top-hit, measured on the same queries the gate then scores. So "0 of ≥4 null queries return any hit" passes by construction whenever the ranges don't overlap. — Any embedder or floor passes the gate on its own calibration set. — Split the dataset: calibrate on one set of null and labelled queries, then gate on a held-out set (at least 4 null and 4 labelled, written separately). Record both splits' sha256 in the report. — resolved: held-out split for all gates; both split sha256s in the report.
- [x] **BLOCKER** "Never raises" is only tested by calling the Python function directly. FastMCP validates arguments against the signature (`filters: dict | None`, `limit: int`) before the handler runs, so `filters="witt"`, `limit="abc"` or a missing `query` return an SDK/protocol error, not `{"ok": false}`. The stdio round-trip only covers API-down. — Broken implementation that passes: today's design as written. — Add `test_mcp_tool_bad_argument_types_return_ok_false`, driven through an in-memory `ClientSession` / `mcp.call_tool`: `filters` as a string, `filters` as a list, `limit="abc"`, `limit=0`, `query=""`. Assert each result is the tool's `{"ok": false, "error": …}` payload, not `isError`. Otherwise type the parameters loosely (`Any`) and validate inside the handler. — resolved: tool tests run through an in-memory ClientSession; semantic-invalid args → ok false; wrong-type args → SDK isError, with the claim narrowed in Interfaces.
- [x] **BLOCKER** The recall eval has no test that it fails when a hard gate fails. There are scenarios for metric math and API-down only. — An eval that writes the report and always exits 0 passes. — Add `test_recall_eval_exits_nonzero_on_failed_gate`, parametrized with a stubbed HTTP transport over: a non-`Witt/` path in a witt-scope response, a `Wiki/` path in a vault-scope response, a null query with one hit, and p95 ≥ 1000 ms. Assert non-zero exit and that the gate's name appears in stderr and in the report. Add `test_recall_eval_calibration_overlap_stops`: overlapping null and labelled ranges give a non-zero exit with "overlap", and no `recall_min_similarity` is suggested. — resolved: gate-failure table scenario (6 gates) plus a calibration-overlap scenario.
- [x] **SHOULD** The snippet contract has no scenario, though the r1 review marks it "resolved". `RecallHit.snippet` says "≤600 chars, cut at the last whitespace before 600", and no Gherkin covers it. — Returning the full `chunk_text`, or `[:600]` mid-word, passes. — `test_snippet_truncates_on_word_boundary`: a 1,000-char chunk gives ≤600 chars ending before a whitespace boundary (no partial word). A 100-char chunk is unchanged. A 700-char chunk with no whitespace has its behaviour pinned (hard cut at 600?). — resolved: snippet rule pinned in RecallHit (last whitespace at or before 600, else a hard cut); covered in tests/test_recall_api.py.
- [x] **SHOULD** The recall log schema isn't asserted. Only "one line with the request_id" and "dropped_below_floor > 0" are checked. — Writing `{"request_id": …, "dropped_below_floor": 1}` passes. — `test_recall_log_line_schema`: parse the line and assert the exact key set from Decision 8. `hits[*]` must equal the response's `(note_path, score, similarity)`, `filters` must equal `applied_filters`, `latency_ms` is a number ≥ 0, and `embedding_model` equals the embedder's `model_name`. Also pin whether 422 and 503 requests write a line. "One JSON line per request" is ambiguous; I'd say 503 yes (with the error type) and 422 no. — resolved: recall_log schema scenario with the exact key set; 503 writes a line, 422 writes none.
- [x] **SHOULD** The concurrency scenario is vacuous with a mocked retriever and doesn't check the log. — A mocked `HybridRetriever` returns identical hits trivially, and lost or interleaved `recall_log` lines go unnoticed. — State that the 8-way test uses real `LexicalStore` and `VectorStore` on the fixture index (`LexicalStore` shares one `check_same_thread=False` connection across `to_thread` workers). Assert 8 distinct `request_id`s and exactly 8 new, individually parseable lines in `recall_log.jsonl`. — resolved: concurrency on real stores with a cold embedder; 8 distinct request_ids and 8 parseable lines.
- [x] **SHOULD** Recall during a reindex is untested. r1 asked for it, and it wasn't added. `_run_indexing` writes and runs `_rebuild_fts` on the same shared `LexicalStore` connection that recall reads. A `ProgrammingError` (a `DatabaseError` subclass) on the read path makes `search` call `_reconnect()`, which closes the connection mid-index. — Nothing catches it. — `test_recall_concurrent_with_index`: run `_run_indexing` over a fixture vault in one thread while 20 recalls run. Assert every recall is either 200 or 503 "recall unavailable: …", and that the index ends complete (chunk counts equal a serial run). — resolved: recall-during-reindex scenario added.
- [x] **SHOULD** The 503 path is tested for embedder failure only. Decision/Interfaces name embedder, Chroma and SQLite. — Catching only `RuntimeError` around `embed_single` passes. — Parametrize `test_recall_retrieval_failure_503` over: `ChromaError` raised on both the first try and the retry, `sqlite3.OperationalError` on both tries, and the embedder `RuntimeError`. Assert the exact detail `"recall unavailable: <Type>"`, that caplog has a record with `exc_info` set, and that the response body contains neither the exception message nor a filesystem path. — resolved: 503 table over embedder, Chroma and SQLite failures; no leaked message or path; exc_info logged.
- [x] **SHOULD** The zero-spans scenario needs a flush, and it needs isolation from the rest of the test session. — With a `BatchSpanProcessor`, asserting "0 new spans" before the batch exports passes even when spans were emitted. `Traceloop.init` also sets the global tracer provider once per process, so test order can make it vacuous. — Specify `SimpleSpanProcessor`, or call `provider.force_flush()` before both the `/ask` control assertion and the recall assertion. Run the test in a subprocess (or a fixture that owns the provider) so it isn't affected by other tests. — resolved: subprocess + SimpleSpanProcessor + force_flush, with a live-instrumentation control.
- [x] **SHOULD** The Langfuse scenario can't observe the real risk, and its probe misses `requests`. With a non-routable host, the startup probe fails, so no OTLP processor is ever attached. The OTLP HTTP exporter also uses `requests`, not `httpx`, so patching `httpx` wouldn't see it. — Any implementation passes. — Use a local TCP listener as the Langfuse host that counts connections. It is reachable, so the processor attaches. Do one recall, `force_flush`, and assert 0 POSTs to `/api/public/otel/v1/traces`. Keep the non-routable case only for the startup-latency claim. — resolved: local counting TCP listener so the processor attaches; 0 POSTs asserted; non-routable case kept for latency only.
- [x] **SHOULD** The project-filter scenario under-asserts.
