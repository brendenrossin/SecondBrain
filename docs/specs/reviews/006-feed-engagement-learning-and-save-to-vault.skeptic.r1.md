## Skeptic review — 006
Verdict: approve with changes

Unstated assumptions:
1. ADR-012 exists and settles "learned state lives in feed.db". It does not exist yet. The only ADR in `.witt/PROJECT.md` is ADR-011, and nothing under `docs/` defines ADR-012. — Not written down.
2. The vote, click and save endpoints can get "the config keywords the item matched" at request time. That means the API process reads `_config/feed.md`, or it reads `rank_why`. The spec never says which. — Not written down.
3. `wiki._start_ingestion_job` validates the URL. It does not: `detect_content_type` is called by the `/wiki/ingest` route (`api/wiki.py:151`), not by the helper. — Not written down. The AC implies it, but the Design says "calls `_start_ingestion_job(url)`" as if that were the whole job.
4. KLIB-1 indexes the saved page. It does not: `_start_ingestion_job` passes no `index_callback`, so nothing is indexed until the next reindex. — The spec claims "→ index", which is wrong.
5. KLIB-1's duplicate check makes a second save harmless. It does not: `find_existing_by_source` makes the pipeline re-fetch, re-audit, re-compile and overwrite the existing Wiki page (`ingestion/pipeline.py:94-106`). — The spec states the opposite.
6. `_start_ingestion_job` must run on the event-loop thread, because it calls `asyncio.create_task`. The existing feed endpoints do their store work inside `asyncio.to_thread`. A builder who copies that pattern and calls the helper from inside the thread gets "no running event loop". — Not written down.
7. Hypothesis is available. It is not in `pyproject.toml` or `uv.lock`. — Not written down. The Files table omits `pyproject.toml`.
8. The migration handles a db at user_version 0, not just 1. The current `_migrate` is one all-or-nothing step guarded by `version >= _SCHEMA_VERSION`. Going 0→2 has to run the v1 backfill and the v2 DDL as separate steps. — Partly written down (the v1→2 AC only).
9. The `ALTER TABLE` can be rolled back. In Python's default sqlite3 mode a DDL statement does not open an implicit transaction, so it autocommits. "Transaction is rolled back" only holds if the builder issues `BEGIN` explicitly. — Not written down. The "add only if missing" guard makes this survivable, but the AC wording is misleading.
10. The sqlite file is written by two processes. The API and the cron each run migrations on open, and they can race on `ALTER TABLE ADD COLUMN` ("duplicate column"). — Partly written down: the risk lists two writers but not two migrators.

- [x] **BLOCKER** ADR-012 is cited as the decision record, but it has not been written, and it conflicts with a stated project principle. CLAUDE.md says "Vault is the single source of truth — no application state outside it". The FeedStore docstring justifies feed.db because items are "derived data … re-fetchable". Votes are neither: they are user intent that cannot be re-derived, and they change behaviour. — This is the spec's whole Non-Goal #1, and it rests on a decision nobody has written down. — Fix: write ADR-012 (note_write) before approval. Name the principle exception explicitly, and say why signals are acceptable outside the vault: reset-able, bounded, visible in the panel. — won't fix: ADR-012 exists in the vault (Witt/Projects/second-brain/decisions/ADR-012-…), written by note_write on 2026-11-22. The principle exception is now named explicitly in v0.2.0 Decision 1.

- [x] **BLOCKER** The source of `keywords` for `set_vote`, `record_click_signal` and `mark_saved` is ambiguous. Two engineers would build different things. (a) Re-load the vault config in the API on every vote or click and call `matched_keywords`. That adds a vault read to the click endpoint, and when the note is missing `load_feed_config` silently falls back to `SEED_DEFAULTS`. Signals would then be tagged with seed keywords rather than yours, with no error, and `settings.vault_path=None` would raise a TypeError. (b) Read the matched keywords already stored in `rank_why`. That is free and matches "explain the score that was used", but it is NULL for rows from before v2. — The outcome differs, and so does the failure mode the spec says must surface as a 500. — Fix: pick (b), with a fallback of empty keywords plus a log line when `rank_why` is NULL. State it in Decision 1 and change "at vote time" to "at rank time". — resolved: v0.2.0 Decision 2. Keywords come from the stored rank_why (rank time), with [] plus an INFO log when NULL. The API never reads the vault config on a vote, click or save.

- [x] **BLOCKER** The save semantics contradict themselves and can mislead. `mark_saved(item_id, keywords) -> url` is both the lookup and the stamp. The 422 and 500 ACs need `saved_at` to stay NULL, so validation must happen before the stamp, and the interface makes that awkward. Worse, `saved_at` is stamped when the job *starts*. A safety-audit block or fetch failure (paywalls, HN links) leaves `saved: true` and a +1 signal on reload, even though nothing reached the vault. — Goal 4 says "Save … to the vault", and the persisted flag would lie. — Fix: split it into `get_item_url(id)` → `detect_content_type` → `_start_ingestion_job` → `mark_saved`. Then either document `saved` as "save requested", or set it only when polling reports complete (needs a small callback). Also say what a second tap does: return 409, or no-op when `saved_at` is set, because KLIB-1 will otherwise re-spend and overwrite a Wiki note you may have edited. — resolved: v0.2.0 Decision 4. Ordered flow get_item → detect → claim → start (on the loop) → signal. saved counts only when on_complete reports COMPLETE. 409 on a second save. A failed job sets error and allows retry.

- [ ] **SHOULD** "Both are written in one transaction" (Decision 5) won't hold if the builder uses the store's `_run` helpers. `_run` reconnects and retries one statement on a DatabaseError, and the reconnect rolls back the earlier statement. You end up with the signal written and the vote not, which is the exact hazard the comment in `replace_section_overviews` warns about. — Fix: require `set_vote` and `mark_saved` to use a single `with self.conn:` block with no per-statement retry, and add a test that forces the second statement to fail.

- [ ] **SHOULD** A failed migration is described as leaving "the db usable", but "usable" is never defined. If the v2 columns are missing, `add_items` writing `rank_why` raises, so every daily refresh fails. `daily_sync` swallows the error, so the feed silently goes stale. `_to_item` runs outside `_fetch_recent`'s try, so `row["vote"]` would make `GET /feed` return a 500, breaking the never-raises promise. — Fix: say what degraded mode means. For example, readers use `row.get`, and the writers skip `rank_why` when the column is absent. Add an AC that `GET /feed` and `run_feed_pipeline` both work at user_version 1.

- [ ] **SHOULD** The day-28 product check cannot measure what it claims. Saves write `kind='up'`, so "≥ 15 thumbs votes" counts saves as thumbs. A Reset (`DELETE FROM feed_signals`) also wipes the evidence the check depends on. — The spec's own kill criterion is unreliable. — Fix: add `kind='save'` (value +1.0), or an `origin` column. Make Reset either soft (an `archived_at`) or log the deleted count via `log_append`/UsageStore so the check survives it.

- [ ] **SHOULD** The float ACs will fail as written. In Python `1 + 0.1*3` is `1.3000000000000003`, and a "fresh" signal created a few milliseconds before `now_ts` decays slightly. "Is 1.3", "is 1.025" and the `≠ 1.0` filter on `/feed/learning` are all exact comparisons. — Fix: have `compute_adjustments` round multipliers to 3 dp (identity is unaffected, because empty maps stay at 1.0), or state `pytest.approx` and a tolerance for the ≠ 1.0 filter.

- [ ] **SHOULD** Several sequence cases are left undefined. What does `none` do after a click then 👍: restore the click signal or leave none? Does a vote change reset `created_at`, and with it the decay clock? A URL pruned and later re-fetched gets a new `feed_items` row with `vote` NULL while its old signal survives. Does "no thumbs vote" for click gating check `feed_items.vote` or `feed_signals.kind`? With the former, a click would overwrite a surviving 'up'. — Fix: one line each in Decision 5/6, with the gate checking `feed_signals.kind`.

- [ ] **SHOULD** Putting the controls inside `FeedLink` means `<button>`s nested in an `<a>`, which is invalid interactive content. It needs `preventDefault` + `stopPropagation`, and screen readers handle it badly. `FeedBlock` can also pass `id={undefined}` when a section item falls outside `feed_page_limit`. — Fix: say the row becomes a container with the anchor and the controls as siblings, and that the controls are hidden when `id` is undefined or `href` is unsafe.

- [ ] **NIT** Keyword credit is not split across matched keywords. Generic keywords like "model" (weight 1.0) match the most items and will learn fastest. The source and keyword effects also compound on one vote (≈1.1×1.1). If that's intended, say so in Risks.

- [ ] **NIT** Goal 4 says "safety audit included", but a missing `ANTHROPIC_API_KEY` makes `get_safety_auditor` raise a RuntimeError inside `_start_ingestion_job`. Map that to 500 the same way `/wiki/ingest` does, and add it to the error list.

- [ ] **NIT** The "≈ 2026-12-20" date is pinned to the spec's draft date, not the ship date. Make it "28 days after rollout".

Cheaper alternative considered: Ship in two slices. Slice 1 is votes, save and sendBeacon, with `rank_why` shown read-only. Slice 2 (`learn.py`, the rank change, the learning panel and reset) ships only if the day-28 check shows ≥15 real thumbs. Until then, the vault weights you already control in `_config/feed.md` are a fine manual knob. The spec's own Risks section admits the thumbs habit is unproven, and slice 2 is where most of the migration, UI and test surface lives.
