## Architect review — 001
Verdict: approve with changes

- [x] **BLOCKER** Goal 5 and Decision 6 ("recall adds no spans", "`data/traces/*.jsonl` gets no new span shapes") are false as designed. When `tracing_enabled` is true, `init_tracing` calls `Traceloop.init(...)` (`/Users/brentrossin/code/second-brain/src/secondbrain/tracing.py:95`). That auto-instruments ChromaDB for the whole API process. Every recall `collection.query` will therefore emit a `chroma.query` span into the JSONL. The traces already contain them: 285 `chroma.query` spans across 16 files in `data/traces/`. Not importing `secondbrain.tracing` in `api/recall.py` changes nothing, because instrumentation is process-wide and recall runs inside the API. — This matters because it is a stated Goal. The trace-eval tests read the live `data/traces` directory, so N Claude sessions calling recall will fill it with retrieval-only root traces. — Fix: pick one and write it into the spec and a test. (a) Restate the goal as "no new span *shapes*: recall emits the same auto-instrumented `chroma.query` spans `/ask` does, and its latency never depends on Langfuse (BatchSpanProcessor is async)". Or (b) actually suppress spans: run the retrieval under OTel's instrumentation-suppression context key, and add a Gherkin step "with tracing enabled, a recall writes 0 spans to the JSONL". — resolved: v0.2.0 Decision 7, retrieval runs under suppress_instrumentation() inside the worker thread; Goal 6 + scenario 'recall writes zero spans with tracing on' (Brent chose suppress).
- [x] **SHOULD** The design diagram, Decision 3, Decision 4 and two Gherkin scenarios name `check_and_reindex` as the reindex path inside the API process. It isn't. `check_and_reindex` (`api/dependencies.py:277`) is only called from the deprecated Gradio `ui.py` (lines 438, 636). In production, `make index` and `daily_sync.reindex_vault` both reach `POST /api/v1/index` → `_run_indexing` (`api/index.py:53`), which runs its own classify/delete/`remove_file` loop. It also never takes `.reindex_lock` or writes `.reindex_epoch`, so Decision 1's "lock would be bypassed" argument is weaker than stated. The epoch argument still holds. — Fix: point the "previously indexed logs are removed" and "malformed frontmatter skips the note" scenarios at `_run_indexing`, or at both paths. Correct the diagram so `/api/v1/index` → `_run_indexing` → `VaultConnector`. — resolved: diagram/Decisions 3-4/scenarios now target POST /api/v1/index → _run_indexing; Decision 1 lock claim corrected; check_and_reindex noted as deprecated in Non-Goals.
- [x] **SHOULD** The spec never says what `top_k` recall passes to `retrieve`. `retrieve` cuts to `top_k` chunks *before* recall dedupes per note and applies the `project`/`kinds` post-filters. Passing `top_k=limit` will regularly return fewer than `limit` hits: one note's three chunks fill the window, or a `kinds` filter discards most candidates. — Fix: state that recall calls `retrieve(query, top_k=k_vec + k_lex, note_folder=...)`, i.e. the whole fused candidate set, then post-filters, dedupes, and slices to `limit`. Add a Gherkin case: "limit 5 with a kinds filter returns 5 when ≥5 matching notes exist". — resolved: Decision 6 fixes the pipeline order with top_k = k_vec + k_lex; under-fill scenario added.
- [x] **SHOULD** Filter semantics are undefined outside the default case. What do `project` and `kinds` do with `scope="vault"`? Does `project` drop every non-Witt note? Does `kinds=["note"]` with `scope="witt"` always return empty, or is it a 422? — Fix: define it, e.g. "`project` and Witt `kinds` apply only to Witt hits; `kinds=["note"]` is only valid with `scope="vault"`, otherwise 422". Add those cases to the validation table. — resolved: Decision 6 filter semantics; kinds=['note'] with scope=witt → 422; new 'other' kind; validation rows added.
- [x] **SHOULD** The lexical pre-filter needs a join that the Interface hides. `search` queries `chunks_fts` alone (`stores/lexical.py:242`). `AND chunks.note_folder = ?` requires `JOIN chunks ON chunks.rowid = chunks_fts.rowid`. The filter must also be applied on the reconnect-retry branch in both stores, because each has a duplicated retry block. — Fix: put the join in the Interface note. Make the prefilter test cover a result set larger than `LIMIT`, so filtering provably happens before the limit and not after. — resolved: Interfaces pin JOIN chunks c ON c.chunk_id = chunks_fts.chunk_id + parameterized IN; retry-branch scenario; >LIMIT result-set scenario.
- [x] **SHOULD** The 10s MCP timeout versus a cold embedder. `get_embedder` loads bge-base lazily on the first `embed_single`. After a KeepAlive restart, the first recall pays the model load, which can approach or exceed 10s. That returns `ok=False`, and the skill may treat it as "no prior art". — Fix: either warm the embedder in the API `lifespan` (startup change only, no contract change), or make the timeout error say "timed out (API may be warming up; retry)". Decide now rather than "verify during implement". — resolved: Decision 9 optional embedder warmup (on in Rollout via .env); timeout error says 'retry once'; no auto-retry.
- [x] **SHOULD** Runtime dependency on `httpx`. `httpx` is declared only under `dev` extras (`pyproject.toml:40`). It currently arrives transitively, through `mcp` and through `tracing.py`'s import. — Fix: add `httpx` to the main `dependencies`, since `mcp_server.py` imports it directly. Add `uv sync` to Rollout step 2 so the `secondbrain-mcp` console script exists in `.venv/bin` before step 5 registers it. — resolved: httpx moved to main deps; Rollout step 2 runs uv sync.
- [x] **NIT** The `Witt/Logs/*` exclude is global. `extract_metadata` in `daily_sync`, `api/metadata.py` and suggestions also stop seeing logs, which is good for cost. But existing `metadata.db` rows for logs are never deleted, because `get_stale` only looks at current files. Mention this in Data, or accept the orphans explicitly. — resolved: accepted in Non-Goals (orphaned metadata.db log rows are harmless).
- [x] **NIT** `"Witt"` (scope folder) and `"Witt/Logs/*"` (exclude) are hardcoded in two modules alongside `classify_witt_path`. Put them in one constant next to `classify_witt_path` so a layout change is a single edit. — resolved: vault/witt.py owns WITT_FOLDER, WITT_LOG_EXCLUDE, RECALL_VAULT_EXCLUDES and classify_witt_path.
- [x] **NIT** A sync `@mcp.tool()` doing blocking httpx is fine for a one-tool stdio server. An `async def` with `httpx.AsyncClient` would avoid blocking the MCP event loop for up to 10s. — resolved: MCP tool is async with httpx.AsyncClient.

Decisions worth an ADR: (1) the thin HTTP client: MCP never opens the stores, and the API is the single owner (Decision 1); (2) removing `Witt/Logs/*` from the global index, which also changes `/ask` (Decision 3 and the open question); (3) taking kind and project from Witt's path layout, which couples SecondBrain to Witt's v0 Data contract (Decision 5).
