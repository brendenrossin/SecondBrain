## Skeptic review — 001 SecondBrain recall MCP server for Witt (v0.4.0, round 4)
Verdict: approve with changes

Unstated assumptions:
1. **The step-0 numbers describe the production index.** Step 0 ran with "no blurbs". But `context_generation_enabled` defaults to `True` (`config.py:79`), and `_run_indexing` puts Haiku blurbs into the embedding text whenever an Anthropic key is set (`api/index.py:106-110`, `build_embedding_text`). So the 0.459 identifier similarity that Decision 12 uses to justify the 0.40 floor may not match what the live API scores. Not written down. The Evals section records the blurb count but doesn't connect it to the floor rationale.
2. **A filtered Chroma query with `n_results >= Witt count` returns every Witt chunk with its exact cosine.** Decision 6 says keyword-only candidates fall below the floor "by construction". That only holds if HNSW plus the `where` filter is exhaustive. It also uses the lexical count to size the vector window, which assumes the two stores agree (they can differ mid-reindex). Not written down, and no real-store test covers it.
3. **One `LexicalStore` sqlite connection is safe to share across concurrent recall threads and the indexer thread.** It's a single `check_same_thread=False` connection from `lru_cache`. Its reconnect-on-`DatabaseError` path (`lexical.py:252-255`, and the same pattern in the new `count_chunks`) closes the connection the indexer may be in the middle of using. The "recall during a reindex" scenario tests this, but the spec doesn't say what to do if it fails. Not written down.
4. **A Claude Code agent can't simply read the 7 Witt notes itself.** The whole Worth case rests on this, and it isn't argued anywhere.
5. **The newsyslog conf already exists**, so "Update" in the Files table is correct (`etc/newsyslog.d/secondbrain.conf` has no `recall_log` entry yet). Written down in Files and Rollout 7. OK.

- [x] **BLOCKER** The eval's dataset validation rejects the dataset it requires. The dataset must have "≥2 identifier queries (an ADR number, a function name)" and "≥1 one- or two-token query". Validation refuses to run on "a query found verbatim in any vault note". An identifier query like an ADR number or a function name appears verbatim in its own expected note by definition, and that note is a vault note. A one- or two-token query will almost certainly appear somewhere in the whole vault. So `recall_eval` exits non-zero on every compliant dataset, and Rollout step 5 can never pass. — It blocks the rollout gate outright. An implementer will quietly weaken one of the two rules, which defeats the "don't edit to pass" discipline. — Apply the verbatim check only to queries of, say, ≥8 words, or only to labelled queries that aren't identifier or short queries. Name the exemption in the dataset schema (for example `kind: identifier|short|long|prose`) so the validator can enforce it. — resolved: v0.5.0: queries carry kind; verbatim check applies to prose and long queries only, scoped to the Witt corpus; exemptions have their own AC.
- [x] **BLOCKER** The pinned description contradicts the Non-Goal it rests on. The description says "`similarity` (0–1) is comparable across queries". The Non-Goals cite step-0 data and BAAI's guidance that bge cosines aren't absolute relevance scores. Unrelated queries' best match scored 0.469–0.594, which overlaps the expected-note range from 0.459 up. Telling the calling LLM the number is comparable invites it to treat 0.55 as "strong". That's exactly the over-trust risk listed first in Risks, and the pinned description is its only mitigation. — The spec's top risk is made worse by the spec's own pinned text, and changes to that text are spec changes. — Replace the clause with something like "`similarity` and `score` only order hits; neither is a relevance verdict". Then update the pinned-description AC. — resolved: v0.5.0: pinned description now says similarity and score only order hits in this call and neither is a relevance verdict.
- [x] **SHOULD** Scope the null-query `must_not_appear` grep to the indexed Witt notes, not "the vault". Null queries are defined as "topics no Witt note covers". Near-miss terms will often appear in the thousands of non-Witt notes (`10_Notes`, `Wiki/`), so the "null contamination" check will reject good near-misses for the wrong reason. Two engineers would scope this differently. The same scoping question applies to the verbatim check. — resolved: v0.5.0: must_not_appear and verbatim checks are scoped to the Witt corpus (glob minus DEFAULT_EXCLUDES); AC row for a 10_Notes-only term.
- [x] **SHOULD** Re-anchor the floor rationale to the production index, or say it doesn't matter. Decision 12 justifies 0.40 with a no-blurb measurement (assumption 1). Keyword-only candidates are dropped, so BM25 can no longer rescue an identifier query whose cosine slips under 0.40. The ADR-002 margin is 0.059 on a 7-note corpus. — Either re-run step 0 against the blurbed index and quote that number, or add `expected_similarity` to the eval report for identifier queries and say that a floor within 0.05 of any expected similarity is a stop-and-ask. — resolved: v0.5.0: floor_margin hard gate on the live blurbed index (expected similarity ≥ floor + 0.05), stop and ask Brent on failure (Decision 12).
- [x] **SHOULD** Don't commit a binary Chroma directory as a fixture. "A small committed fixture index" means checking in a `PersistentClient` directory tied to chromadb 1.4.1's on-disk format. Opening it can migrate or touch files, which dirties the tree after a test run and breaks on any chromadb upgrade. Several scenarios (concurrent recalls on real stores, recall during a reindex) also write to stores. — Commit fixture markdown plus the stub embedder plus the goldens (JSON). Build the index into `tmp_path` per test session. State that write scenarios always use a copy. — resolved: v0.5.0: commit fixture markdown + stub embedder + golden JSON; build the index into tmp_path per session; write scenarios use a copy.
- [x] **SHOULD** Say what to do if the shared-connection concurrency AC fails (assumption 3). — Add one line: if "recall during a reindex" or "concurrent recalls" is flaky, recall gets its own read-only `LexicalStore` connection (`mode=ro` URI) and doesn't reuse the shared one. Otherwise the implementer improvises a locking change to a store that `/ask` depends on. — resolved: v0.5.0 Decision 1: fixed fallback is a read-only lexical connection for recall; never change locking in the shared store.
- [x] **SHOULD** The MRR gate trigger is ambiguous. "Becomes a gate … as soon as any labelled query's expected rank is greater than 3." Does it apply in the same run, so the run that first sees rank 4 can fail on MRR, or from the next run on? And who records that it has flipped? Two engineers would build different behaviour. — Either make the flip explicit (for example a `gate_mrr: true` key in `recall_queries.yaml` that the eval tells Brent to set), or make it a same-run rule and add it to the gate-failure AC table. — resolved: v0.5.0: explicit gate_mrr key in the dataset; the eval only recommends; AC for both triggers.
- [x] **NIT** "By construction" in Decision 6 overstates assumption 2. Add a real-store fixture test that with floor 0 and `k_vec = count`, vector search returns exactly `count` Witt chunks. Or soften the wording. — resolved: v0.5.0: 'by construction' replaced by a stated assumption, pinned by the real-Chroma window AC.
- [x] **NIT** Intent promises results "in under a second", but the latency gate uses server-side `latency_ms` only, which excludes MCP stdio and HTTP overhead. Either say the bound is server-side, or have the eval also record client wall time (report-only). — resolved: v0.5.0: Intent says under a second server-side; client wall time is reported, not gated.
- [x] **NIT** The "vault_path set but directory missing" condition emits "vault path not configured…". The wording is inaccurate for that case. Use "vault path missing or not configured; project slug not verified". — resolved: v0.5.0: notice text is now 'vault path missing or not configured; project slug not verified'.
- [x] **NIT** Decision 3 (dropping `Witt/Logs/*` from the global index) changes `/ask` and metadata behaviour. Recall doesn't need it, since a path filter in recall step 7 would do. It's Brent's recorded call, but it's a separable change bundled into a recall spec. If it's kept, the Undo should note that `/ask` regains the logs. — resolved: kept (Brent's earlier call); Undo now notes /ask and metadata see Witt logs again.
- [x] **NIT** On a case-insensitive macOS filesystem, `exclude_paths` exact match fails if the caller's case differs from the indexed path. Say "exact, case-sensitive match against `note_path`" so the follow-up Witt spec passes the mirror path verbatim. — resolved: v0.5.0: exact, case-sensitive match against note_path, with an AC row for a different-case path.

Cheaper alternative considered: With 7 non-log Witt notes, a Claude Code agent running Grep or Read over `~/Obsidian-Vault/main-vault/Witt/` (or a ~20-line Witt-side `note_search` doing BM25 over its own notes) gets the same "have I solved this before?" answer with zero cross-repo HTTP, no store changes and no eval harness. This spec pays off only once Witt reaches dozens of notes. It's worth doing now only if Brent wants the infrastructure in place ahead of that growth. That's a legitimate choice, but it's a choice, not a necessity.
